# ML model ops: model cards, reasons, drift, account links, crowd 3D, replay

Added 2026-11-25. Every model is still **shadow-only**: nothing below changes checkout, payment, ticket validity,
gate admission, prices or accounts, and there is no promotion path.

## 1. Honest metrics

- `apps/ml-service/models/model_metrics.json` (near-perfect legacy scores: fraud accuracy 1.0, intent R² 0.976,
  produced because the old labels were formulas of the features) is **deleted**.
- `GET /models/metrics` now serves a summary of the gated reports in `reports/v0/` (status, model vs the current
  rule on the newest unseen 15%, 95% interval of the improvement).
- `reports/v0/README.md` is regenerated by every training run that includes all v0 models.

## 2. Model card (`/admin/ai-models?model=<name>`, SUPER_ADMIN)

Linked from every model on the AI monitor. API: `GET /api/ml/ops/:name` → `monitor.js modelOps()`.

| Panel | Source | Live or offline |
|---|---|---|
| Offline test, AI vs rule across 5 time slices | `report.diagnostics.over_time` | offline (test period) |
| Calibration (binary models) | `report.diagnostics.calibration` | offline |
| Forecast range coverage (demand) | `report.diagnostics.range` | offline |
| What the model relies on | permutation importance, `report.diagnostics.importance` | offline |
| Why it scored these | two worked examples with reasons | offline |
| What the account links add (fraud) | `report.diagnostics.without_link_features` | offline |
| Live input drift | PSI of the inputs logged with the last 14 days of SHADOW rows vs the artifact's training profile | **live, inputs only** |
| Must-not-get-worse checks | `report.guards` | offline |
| Blind fraud reviews (fraud) | `/ml/fraud-review-metrics` + `/ml/fraud-review-cases` | live |

The rule from Step 6 still holds: **no accuracy figure is computed from live traffic** (it includes internal and
test activity). Drift needs no outcome. Reviewed fraud cases are only shown once their blind review is resolved,
and only to super admins.

The diagnostics are computed after the status, thresholds and settings are fixed, so they cannot change a result.

## 3. Reasons for a prediction (`ml/explain.py`)

For each input, the prediction is recomputed with that one input set to its typical training value (median /
most common). The difference is that input's effect; the three largest are reported.

- Stored with every SHADOW row of `fraud`, `demand`, `demand_hourly`, `crowd` (`shadow.js EXPLAINED_MODELS`).
  Per-customer models with big batches are left out to keep the 15-minute jobs fast.
- Shown on the organizer demand panel (live reading), in the model card's examples, and beside resolved fraud
  reviews. **Never in the blind review queue.**
- Limits, stated wherever they are shown: one input at a time, so the effects do not add up to the prediction and
  ignore interactions; a calibrated probability moves in steps, so small effects may read 0.

Every artifact now carries `reference` (typical values + decile / category shares of the training rows):
`GET /v2/reference/{name}?sha256=` (fingerprint-checked) serves it for the drift check.

## 4. Account links in the fraud model

New inputs (`accountLinks.js`, generator 2.3.0), all as of the checkout:

| Input | Meaning |
|---|---|
| `linked_accounts` | other accounts that had the same phone number (digits, last 10) or used the same browser (`x-session-id`, kept in localStorage) |
| `linked_accounts_confirmed_fraud` | of those, accounts with an order whose latest review before the checkout is CONFIRMED_FRAUD |
| `linked_orders_same_event_24h` | their orders for the same event in the previous 24 h |

- Exported fraud rows need the three values in the logged snapshot; older snapshots are skipped
  ("snapshot taken before account-link inputs"), never reconstructed.
- **Account graph** on each investigation (`GET /api/ml/account-graph/:userId`, SUPER_ADMIN): accounts up to two
  steps away, phone links solid, browser links dashed, confirmed fraud marked. Loaded only on request; viewing it is
  logged as detector exposure for every account shown, so that admin's later reviews of them are not blind.
- Synthetic assumption (generator README): bot rings often share phones and browsers (65% of bot accounts are in a
  ring), 6% of legitimate customers share a family phone or browser, 2% of orders get an unrelated link. The gain
  on synthetic data is partly built in; the real gain can only be measured on blind-reviewed real orders.
- Limits: the phone number is the current one (no history); phone matching scans the users table (add an
  expression index on the normalised number at scale); a developer signing into many test accounts from one
  browser links them all.

## 5. Crowd flow in 3D (Gate management → Live)

The event's own 3D venue; every seat takes the colour of its gate's load (scans per 5 min × 12 / capacity per
hour) in the chosen slot, for the rule estimate, the shadow model (when this viewer may see it) or the actual
scans. Gate per seat comes from the gate load plan (section, rows). OK / Busy (over 85%) / Over capacity, each with
an icon and a label, plus a table of the same numbers. Read-only.

## 6. Demand range band

The organizer demand panel draws the model's 80% range on a 0..capacity track with the forecast and the rule's
estimate, and states how often that range held the real number in the offline test
(`registry.evaluation.range_coverage`).

## 7. Replay (`python -m ml.replay`)

Compares any two model files on the same rows: only rows newer than both models' training data; each model with
its own inputs and threshold; 95% interval from resampling whole events. With a database export the rows are the
logged shadow traffic (inputs as logged, outcomes attached later). It registers, promotes and deploys nothing.

```
python -m ml.replay --model fraud --a models/v0/fraud.joblib --b models/candidates/<stamp>/fraud.joblib --data exports/<stamp>
```

# Round 2 (2026-11-26): demo simulator, public / real data, fairness, crowd overload, readiness, governance report

## 8. Demo traffic simulator (`apps/api/scripts/ml-demo-simulate.mjs`)

```
node scripts/ml-demo-simulate.mjs --setup-gates --with-tickets 2000 --yes   # fill the AI pages
node scripts/ml-demo-simulate.mjs --reset --yes                             # remove every trace
```

Plays activity through the app's own ML code (feature builders, rules, shadow logging with the real ML service,
the review sample, blind reviews, the visit and crowd jobs): ~100 customers (half with an earlier purchase), a
family sharing a phone, a bot ring of 6 accounts sharing 2 phones and 1 browser (half machine-speed, half
human-speed). On a fresh copy: the rules flagged 11 of the ring's 21 orders (the machine-speed ones), the shadow
model would have flagged all 21, and none of the 86 ordinary orders.

Safe by construction: accounts are `@demo.test` (a test domain in `dataPolicy.js`, so never exported for training),
payments are MOCK (no server-verified evidence: also never exported), prediction rows carry `output.demo =
"simulator"`, gates are named `Demo gate …` and only added to an event without gates. Refuses NODE_ENV/ML_ENV
production; needs `--yes` on a database not named `*_verify`. `--reset` frees the seats it sold.

## 9. Public and real data on the model card

- `python scripts/fetch_public_datasets.py --only credit_card_fraud` (ULB card fraud, OpenML 1597, licence "Public",
  citation Dal Pozzolo et al. 2015) and `python -m ml.public_experiment fraud`: the fraud METHOD on real recorded
  fraud. Chronological split, isotonic calibration, threshold fixed at 1% false flags on the calibration period:
  85% of frauds caught vs 1.3% for a "largest amounts" rule, 0.89% false flags; 11% of flags are fraud at a 0.13%
  base rate (85x random). Card fraud is not scalping: method evidence, not TicketLedger evidence.
- Purchase intent keeps the UCI Online Shoppers experiment (honest variant: 38% buyers in the top 10% vs 22% rule).
- `GET /v2/public-report/{name}` (intent, fraud) and `GET /v2/real-report/{name}`: the newest
  `reports/candidates/<stamp>/<name>.json` trained on a **db-export** (synthetic candidates never count). Until the
  platform is live the model card shows "waiting for live data".

## 10. Fairness check (`report.diagnostics.fairness`)

The offline test split by city, event type, payment method and first-time vs returning customers. Flagged:
fraud = false flags over 1% and over twice the overall rate; other binary models = predicted rate off by more than
5 points; forecasts = worse than the rule in the group. Informational: never changes a status (gates are fixed).
Current flags (synthetic): fraud: first-time customers, Faisalabad; checkout abandonment: Faisalabad, Islamabad;
crowd: conference, qawwali events.

## 11. Crowd: 80% range and chance of going over capacity

Split-conformal scaled residuals (validation period) give each slot an 80% range and the chance that scans exceed
the gate's capacity (per hour / 12), calibrated with isotonic regression on the validation period (within 5 points
of what happened in every tenth of the test slots). Served with every crowd shadow prediction (`low`, `high`,
`p_over_capacity`) and shown in the 3D view when "AI model (shadow)" is selected.

## 12. Go-live readiness (`/admin/ai-readiness`) and governance report (`/admin/ai-report`)

`GET /api/ml/governance` (SUPER_ADMIN). Per model, nine conditions: registered in shadow, trained on TicketLedger
data, offline test passed, real-data test passed, fairness, enough live outcomes, inputs stable, live shadow check
(not built, on purpose), admin approval (no path exists). Verdict is always STAYS_SHADOW. The report page prints
to PDF (browser print): principles, offline results, fairness, live monitoring, public / real evidence, readiness.
